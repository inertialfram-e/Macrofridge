# Research: PowerSync Backend Sync Rules

**Date**: 2026-03-08

## 1. Executive Summary
The goal is to define and implement the synchronization rules in the PowerSync service configuration (`powersync.yaml`). These rules will ensure that users only receive data they are authorized to access, specifically focusing on household-level isolation for inventory and transaction data.

## 2. Technical Context
- **Affected components**: `powersync.yaml` in the root directory.
- **Current behavior**: Placeholder rules allow all reads/inserts for `users` and `households`.
- **Logic and data flow**: PowerSync uses its own DSL for sync rules. It can access the JWT claims provided by the connector (Supabase).

## 3. Findings & Analysis
- **Authentication Integration**: PowerSync can access the Supabase user ID via `request.auth.sub`.
- **Relationship Mapping**: To filter by household, we need to join the target table with `household_members`. 
- **Rule Requirements**:
  - `users`: Users should only sync their own profile.
  - `households`: Users should only sync households they are members of.
  - `inventory_items`: Users should only sync items belonging to their households.
  - `transactions`: Users should only sync transactions belonging to their households.
  - `products`: This is a global catalog and can likely be synced to all users (or filtered if it grows too large).
- **Security DSL**: PowerSync rules use a specific YAML syntax for filtering, e.g., `where: "id IN (SELECT household_id FROM household_members WHERE user_id = token_id())"`.

## 4. Technical Constraints
- Performance: Overly complex subqueries in sync rules can impact replication latency.
- DSL Limits: The PowerSync rule language is powerful but has specific syntax constraints compared to raw SQL.

## 5. Architecture Documentation
Sync rules act as the "gatekeeper" in our offline-first architecture. They define the partial replication set for each client, ensuring data privacy and efficient bandwidth usage by only sending relevant updates to each device.
