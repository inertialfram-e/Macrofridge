# Research: Implement Postgres Database Schema

**Date**: 2026-03-08

## 1. Executive Summary
The project has the basic infrastructure for a Postgres database (via `docker-compose.yml`) but currently has no defined schema, tables, or migrations. The database is a "blank slate" ready for the implementation of the core domain model.

## 2. Technical Context
- **Affected components**: Root directory (migration/setup scripts), Postgres database.
- **Current behavior**: No database tables or schema currently exist.
- **Logic and data flow**: N/A.

## 3. Findings & Analysis
- **Current Infrastructure**: `docker-compose.yml` (line 2) defines a `postgres:15-alpine` container named `macrofridge-db`.
- **Sync Configuration**: `powersync.yaml` (line 10) refers to a publication `powersync_publication` and a slot `powersync_slot`, but these have not been created in the database yet.
- **Schema Requirements (from PRD)**:
  - `Users` table for macro goals and personal data.
  - `Households` table for grouping users.
  - `Household_Members` for many-to-many relationship.
  - `Products` global catalog for barcodes and nutrition.
  - `Inventory_Items` for household-specific inventory and "use soon" tracking.
  - `Transactions` for grocery spend analytics.

## 4. Technical Constraints
- The schema must be compatible with PowerSync's logical replication.
- All primary keys must be UUIDs to support offline creation and avoid collisions.
- The database must enable a publication and replication slot for PowerSync.

## 5. Architecture Documentation
The database is the "source of truth" in our offline-first architecture. It will handle the primary storage of all household data and serve as the replication source for the PowerSync sync engine.
